# Installing v-panel on a server with existing stacks, and migrating the shared infra and apps

[Phiên bản tiếng Việt](migrate-existing-vps.md)

This guide is for servers that already ran docker compose before v-panel: a shared infrastructure stack (Caddy, possibly with PostgreSQL or cloudflared) and app compose stacks installed by hand. v-panel takes them over **in place**. The running example is the server `arm-app-u01`:

| Stack | Folder | Notes |
|---|---|---|
| `infra` | `/opt/infra` | Caddy (publishes 80/443, local CA) + PostgreSQL 18. Creates the `proxy` and `db` networks |
| `n8n-arm` | `/opt/n8n-arm` | Joins `proxy` with the alias `n8n-arm`, data in `./data` |
| `cxml-dev-server` | `/opt/cxml-dev-server/deploy/selfhost` | Joins `proxy` with the alias `cxml-app`; has both `image:` and `build: ../..` |

The hand-written Caddy sites live in `/opt/infra/caddy/sites/*.caddy` and use the snippet `(common)` (`tls internal`, `encode`, `log`) defined in the main Caddyfile.

## 1. What v-panel does and does not do

**It does:**

- Keep the **compose project name** (e.g. `n8n-arm`, not `vp-n8n-arm`). Containers, named volumes (`n8n-arm_…`, `infra_caddy_data`…) and networks stay the same.
- Keep the stack's **folder**. Relative bind mounts such as `./data` keep pointing to the same place.
- Keep the **compose file name** (`compose.yaml` stays `compose.yaml`).
- **Restart nothing and write nothing** in a stack until you press **Deploy** on that instance. On import, the only things written to the stack folder are copies of the original files in `.vpanel-backup/` (and a `.env` when there is none).
- Reuse an alias the service already has on the shared network as the route upstream, without generating `docker-compose.vpanel.yml`, so the container is not recreated.
- Take over a hand-written Caddy site: it is replaced by a `vp-*.caddy` file generated by v-panel. Its other directives (`import common`, `header {…}`…) and its `reverse_proxy` options (health checks…) are kept **verbatim**.

**It does not:**

- Move data or rename volumes and networks.
- Touch Caddy sites that route (`handle`, `handle_path`, `route`, `redir`, `@matchers`, several upstreams). Those stay hand-written.
- Edit any hand-written Caddy file other than a site being taken over.
- Support reverse proxies other than Caddy (Nginx, Traefik).

## 2. Requirements

- Docker Engine with the `docker compose` plugin; root access (`sudo`).
- Stacks started with `docker compose`, so their containers carry `com.docker.compose.*` labels. Stacks that are down are still found when their compose file lives in an adopted root (see section 4).
- Caddy running in a container, with its configuration **folder** mounted on `/etc/caddy` (e.g. `./caddy:/etc/caddy:ro`). If only the Caddyfile itself is mounted, see [section 15](#15-limitations).
- The main Caddyfile imports the sites folder (`import sites/*.caddy`). If it does not, v-panel adds an import line for its own files when the infra is migrated.

## 3. Preparation and backups

v-panel backs up the files it writes. Still, record the current state before a migration:

```bash
docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Label "com.docker.compose.project"}}' > ~/before-ps.txt
```

```bash
docker volume ls > ~/before-volumes.txt && docker network ls > ~/before-networks.txt
```

```bash
sudo tar czf ~/stacks-before-vpanel.tgz /opt/infra /opt/n8n-arm /opt/cxml-dev-server/deploy/selfhost --exclude='*/data/*' --exclude='*/backups/*'
```

- Data in named volumes (databases, `infra_caddy_data` with the certificates and the local CA) is **not touched**, because project names are kept. Back up volumes with your usual procedure if needed.
- Try the whole procedure on a test server first (copy the folder layout and compose files).

## 4. Install v-panel in adopt mode

Clone the repository on the server, then run:

```bash
sudo ./deploy/docker-install.sh --adopt
```

Add `--pull` to use the published image `ghcr.io/lockerbill/v-panel:latest` instead of building from source, and `--yes` to skip the confirmation.

What the script does:

1. Finds the Caddy container (image `caddy`) and uses the network it joins with the most containers as the **shared network**: `proxy` on arm-app-u01.
2. Takes the working folder of every compose project (label `com.docker.compose.project.working_dir`) and maps it to a **root folder**: `/opt/<x>`, `/srv/<x>`, `/root/<x>`, `/home/<user>/<x>`; other paths are kept as they are. For example `/opt/cxml-dev-server/deploy/selfhost` → `/opt/cxml-dev-server`, which also covers the `../..` build context.
   - v-panel's own folder (`/opt/vpanel`) and system folders (`/etc`, `/usr`, `/var/lib/docker`…) are skipped.
3. Prints the list and asks for confirmation. To choose the folders yourself, pass them:

   ```bash
   sudo ./deploy/docker-install.sh --adopt /opt/infra /opt/n8n-arm /opt/cxml-dev-server
   ```

4. Writes two files, which later runs of the installer (upgrades) reuse:

   `/opt/vpanel/vpanel.env`

   ```ini
   VPANEL_SHARED_NETWORK=proxy
   ```

   `/opt/vpanel/docker-compose.adopt.yml`

   ```yaml
   services:
     vpanel:
       volumes:
         - "/opt/cxml-dev-server:/opt/cxml-dev-server"
         - "/opt/infra:/opt/infra"
         - "/opt/n8n-arm:/opt/n8n-arm"
       environment:
         VPanel__SeedInfrastructure: "false"
         VPanel__Defaults__SharedNetwork: "proxy"
         VPanel__AdoptedRoots__0: "/opt/cxml-dev-server"
         VPanel__AdoptedRoots__1: "/opt/infra"
         VPanel__AdoptedRoots__2: "/opt/n8n-arm"
   ```

   - Each folder is mounted into the vpanel container **at the same path**: v-panel writes files there, and the host's Docker daemon reads them with host paths.
   - `AdoptedRoots` are the folders outside `/opt/vpanel/apps` where instances may live. They are not editable in the UI because they must match the mounts.
   - `SeedInfrastructure=false`: the built-in `shared-infra` template is not created (it would clash with the running Caddy).
5. Starts the `vpanel` container on the `proxy` network. If you set "v-panel public URL", Caddy reaches the panel as `vpanel:8080`.

To add or remove folders, run the installer again with `--adopt` and the new list.

**Check the installation:**

```bash
docker inspect vpanel --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
```

```bash
docker inspect vpanel --format '{{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{end}}'
```

```bash
docker logs vpanel --tail 50
```

In v-panel, **Settings > Server > Adopted roots** must list these folders. Refused roots (system folders…) are shown there with a warning.

**systemd mode** (no container): set them in `/etc/vpanel/appsettings.json`:

```json
{
  "VPanel": {
    "AdoptedRoots": [ "/opt/infra", "/opt/n8n-arm", "/opt/cxml-dev-server" ],
    "SeedInfrastructure": false,
    "Defaults": { "SharedNetwork": "proxy" }
  }
}
```

Then give the `vpanel` user read/write access to those folders and run `sudo systemctl restart vpanel`. In this mode Caddy reaches the panel via `host.docker.internal:5080`. The Caddy service of the infra stack needs `extra_hosts: ["host.docker.internal:host-gateway"]` for a route to v-panel itself to work.

## 5. Access v-panel

Open an SSH tunnel and create the admin account as described in the [README](../README_EN.md#accessing-v-panel):

```bash
ssh -N -L 5080:127.0.0.1:5080 <user>@<server>
```

Then open `http://localhost:5080`.

## 6. Scan the server

Open **Import** (left menu) and press **Scan server**. The scan is **read-only**: it uses `docker ps`/`docker inspect`/`docker compose ls`/`docker compose config`, reads the Caddy files, and writes nothing.

The result has three parts:

- **Shared infrastructure**: the stack running Caddy. The *Detected / Current* table compares the settings v-panel would adopt with the current ones; rows marked "→ will change" are changed by the import. It covers: stack folder, shared network, Caddy container, Caddy folder on the host and in the container, ingress (Direct / Cloudflare Tunnel), PostgreSQL (for reference).
- **Hand-written Caddy sites**: every site read from the main Caddyfile and the files it imports (except `vp-*`). The *Can take over* column says:
  - `yes`: the site can be replaced by a generated file;
  - `yes, keeping its directives`: same, with its directives and options kept;
  - `no (reason)`: the site routes and stays hand-written.
- **Apps**: compose projects not managed yet, with their services, status and suggested route (Public URL → service:port, from the Caddy site pointing at the app's alias). **Import** is enabled once the stack is readable and inside an adopted root, and the shared infrastructure has been imported.

Common warnings:

| Warning | Meaning and fix |
|---|---|
| `<dir> is not visible to v-panel. Mount it (installer --adopt)…` | The stack folder is not mounted into the container. Run the installer again with `--adopt` (including that folder). |
| `<dir> is outside the apps root and the adopted roots; add <root> to VPanel:AdoptedRoots.` | Visible but not allowed: add the suggested root. |
| `No adopted roots are configured…` | Installed without `--adopt`. |
| `docker compose config: …` | Docker rejects the stack's compose file, usually because of a variable missing from `.env`. Fix the stack before importing. |
| `Build context <dir> is not visible…` | Does not block the import, but rebuilding needs that folder mounted. |
| `Started with N compose files; they will be merged…` | The stack runs with several `-f`. See [section 15](#15-limitations). |
| `Uses env file <file>…` | The stack uses an env file not named `.env`. Its content becomes the `.env` v-panel writes. |
| `Caddy site '<host>' (…) cannot be taken over (…)` | The site routes. The app can still be imported with an empty Public URL. |
| `Caddy mounts only <file>…` | Caddy mounts a single file. See [section 15](#15-limitations). |
| `Several stacks run Caddy…` | Only the first one is treated as the infrastructure. |

## 7. Migrate the shared infrastructure

Press **Import '<infra>'** on the *Shared infrastructure* card, check the name/slug and press **Import**.

What v-panel does:

1. Copies the original compose file and `.env` to `/opt/infra/.vpanel-backup/<timestamp>/`.
2. Removes the built-in `shared-infra` template if it exists and was never deployed.
3. Updates **Settings**: shared network, Caddy container (e.g. `infra-caddy-1`), Caddy folder (`/opt/infra/caddy` ↔ `/etc/caddy`), ingress.
4. Makes sure the main Caddyfile loads `sites/vp-*.caddy`:
   - If it already imports `sites/*.caddy` (or `sites/*`, `/etc/caddy/sites/…`), **nothing is changed**.
   - Otherwise it backs it up to `/opt/infra/caddy/.vpanel-backup/…`, appends `import /etc/caddy/sites/vp-*.caddy`, runs `caddy validate` then `caddy reload`, and restores the old file on failure.
5. Creates the system app and the **infra** instance, with project name `infra`, in the state `imported · not deployed by v-panel`.

**No container is restarted.**

**Check:**

- In **Settings**, press **Check Caddy**: it must report the Caddy container as reachable.
- In **Instances > infra**: status Running, with the "imported" chip.

Do you need to deploy the infra? No. The infra instance can stay "imported" for good; v-panel still tracks its status and lets you start/stop it and read its logs. When you want v-panel to manage its compose file too, use **Preview deploy** then **Deploy** (section 9).

## 8. Migrate each app

Press **Import** on the app's row. The dialog fields:

| Field | Meaning |
|---|---|
| App name, Slug | Name in v-panel. **The compose project name does not change** (still `n8n-arm`). |
| Public URL | Suggested from the Caddy site pointing at the app. Leave empty to keep the route hand-written. |
| Proxy service, Proxy port | Service and port receiving traffic, from the Caddy site upstream (`n8n-arm:5678` → service `n8n`, port 5678). |
| tls internal | Adds `tls internal` to the generated site. Off when the directives already handle TLS (e.g. `import common`); the caption under the switch says where TLS comes from. |
| Take over the hand-written Caddy site | The first deploy replaces the hand-written site with the generated one. |
| Caddy site directives | Everything in the site except `reverse_proxy`, verbatim, comments included. Placed before `reverse_proxy` in the generated file. |
| reverse_proxy options | The body of `reverse_proxy … { }`, e.g. health checks. |
| Images | **Pull first**: pull every image and build only the missing ones, like `docker compose pull && docker compose up -d`. Suggested when a service has both `image:` and `build:`. **Build**: `up --build`, always rebuilds services that have `build:`. |

After the import:

- The original compose file and `.env` are copied to `<app folder>/.vpanel-backup/<timestamp>/`. If the stack had no `.env`, v-panel creates one with the stack's environment.
- The instance is `imported · not deployed by v-panel`. Its containers keep running; Start/Stop/Restart/Logs use the original compose file.
- You can still back out: **⋮ > Stop managing (keep containers)** removes the instance (and the app created by the import) from v-panel without touching containers, files or Caddy sites.

## 9. Preview and first deploy

On the instance page, press **Preview deploy**. v-panel renders the files it would write (in a temporary folder), runs `docker compose config --hash '*'` and compares the result with the `com.docker.compose.config-hash` label of the running containers:

| Action | Meaning |
|---|---|
| `keep` | The container is kept as is |
| `recreate` | The container is recreated (volumes and data kept, short downtime) |
| `create` | The service has no container yet |
| `remove` | A container whose service no longer exists (orphan) is removed |

If something is unexpectedly `recreate`, read [section 13](#13-troubleshooting) before deploying.

Press **Deploy**. The first deploy, in order:

1. Writes the compose file (same name as the original) and `.env`. The `.env` gets a `# ---- managed by v-panel ----` block on top (`COMPOSE_PROJECT_NAME`, `VPANEL_*`); the rest is the stack's `.env`.
2. Generates no `docker-compose.vpanel.yml` when the proxy service already has an alias on the shared network.
3. Runs `docker compose config`, `pull` according to Images, then `up -d --remove-orphans` with **the same project name**.
4. Writes `sites/vp-<host>.caddy` and removes the hand-written site in **the same** `caddy validate` + `caddy reload`.
   - A hand-written file left with only comments is moved to `/opt/infra/caddy/.vpanel-backup/<timestamp>/`.
   - A file that still holds other sites keeps them; only that site is removed (and the original file is backed up).
   - If validation or reload fails, **both are restored** and the job fails.

**Check after the deploy:**

```bash
curl -kI https://internal.n8n-arm.arm-app-u01/
```

```bash
cd /opt/infra && docker compose exec caddy caddy validate --config /etc/caddy/Caddyfile
```

```bash
docker volume ls > ~/after-volumes.txt && diff ~/before-volumes.txt ~/after-volumes.txt
```

The `diff` must print nothing: no new volume. The instance's **History** tab has the full job log, and the "imported" chip is gone.

## 10. Full example: arm-app-u01

1. `sudo ./deploy/docker-install.sh --adopt --pull`. The script finds the container `infra-caddy-1`, the network `proxy` and the roots `/opt/cxml-dev-server`, `/opt/infra`, `/opt/n8n-arm`.
2. **Import > Scan server**:
   - Infra: shared network `proxy`, container `infra-caddy-1`, folder `/opt/infra/caddy`, ingress `Direct`, PostgreSQL `postgres` on `db` as `infra-postgres`.
   - Sites: `internal.n8n-arm.arm-app-u01` → `n8n-arm:5678` and `internal.cxml.arm-app-u01` → `cxml-app:8080`, both "yes, keeping its directives".
3. Import `infra`. The Caddyfile already has `import sites/*.caddy` and is not changed.
4. Import `n8n-arm`: Public URL `https://internal.n8n-arm.arm-app-u01`, service `n8n`, port 5678; `tls internal` off (TLS comes from the snippet `common`); Images = Build. Preview shows `n8n: keep`. Deploying generates `sites/vp-internal.n8n-arm.arm-app-u01.caddy`:

   ```caddyfile
   # Managed by v-panel. Do not edit: regenerated on every deploy.
   # route n8n-arm -> n8n-arm:5678
   internal.n8n-arm.arm-app-u01 {
   	import common

   	header {
   		X-Content-Type-Options "nosniff"
   		Referrer-Policy "strict-origin-when-cross-origin"
   		-Server
   	}

   	# n8n uses WebSockets for the editor (push); reverse_proxy passes them through.

   	reverse_proxy n8n-arm:5678
   }
   ```

   `sites/n8n-arm.caddy` is moved to `/opt/infra/caddy/.vpanel-backup/…/sites/n8n-arm.caddy`.
5. Import `cxml-dev-server`: service `app`, port 8080; Images = **Pull first** (pulls `ghcr.io/mthpbs/cxml-dev-server`; `backup:local` is built only when missing). The reverse_proxy options keep the health checks:

   ```caddyfile
   	reverse_proxy cxml-app:8080 {
   		health_uri /health
   		health_interval 15s
   		health_timeout 5s
   	}
   ```

## 11. Day-to-day after the migration

- **Edit in v-panel, not by hand**: every deploy rewrites the compose file and `.env` in the stack folder from the template and overrides. Edit the compose file on the app page; env, Public URL, proxy and directives on the instance page.
- `vp-*.caddy` files are regenerated on every deploy too. To change headers or health checks, edit **Caddy site directives** / **reverse_proxy options** on the instance and deploy.
- Snippets in the main Caddyfile (e.g. `(common)`) stay yours. Edit them and reload Caddy as before; v-panel sites that import them pick up the change.
- Other hand-written sites (not taken over) stay as they are. Do not add a hand-written site with the same host as a v-panel route: Caddy would refuse the whole configuration.
- Running `docker compose` by hand in the stack folder still works (same files, same project), but configuration changes must go into v-panel or the next deploy overwrites them.

## 12. Rollback

**Before the first deploy:** **⋮ > Stop managing (keep containers)**. Nothing needs restoring: v-panel only created `.vpanel-backup/` (and `.env` if there was none).

**After a deploy** (n8n as the example; keep this order):

1. Remove the instance from v-panel: **⋮ > Remove deployment…**, with **both** delete boxes **unticked**. The job runs `docker compose down` (containers stop, volumes and files are kept) and syncs the routes, so v-panel deletes `sites/vp-internal.n8n-arm.arm-app-u01.caddy` itself. Then **⋮ > Delete instance**.
2. Restore the stack's files from the import backup:

   ```bash
   cd /opt/n8n-arm && ls .vpanel-backup/
   ```

   ```bash
   sudo cp .vpanel-backup/<timestamp>/docker-compose.yml .vpanel-backup/<timestamp>/.env .
   ```

3. Restore the hand-written Caddy site and reload:

   ```bash
   sudo cp /opt/infra/caddy/.vpanel-backup/<timestamp>/sites/n8n-arm.caddy /opt/infra/caddy/sites/
   ```

   ```bash
   cd /opt/infra && docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile
   ```

4. Start the stack again with its original files:

   ```bash
   cd /opt/n8n-arm && docker compose up -d
   ```

Remove the instance (step 1) **before** restoring the hand-written site. In the other order, the next route sync would regenerate the `vp-*` file for the same host and Caddy would refuse the configuration.

**Removing a folder from the adopted roots:** run the installer again with `--adopt` and the new list.

**Uninstalling v-panel:**

```bash
docker compose -f deploy/docker-compose.yml -f /opt/vpanel/docker-compose.adopt.yml --env-file /opt/vpanel/vpanel.env down
```

The stacks restored above keep running on their own.

## 13. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| An app's Import button is disabled, with "Import the shared infrastructure first" | The shared network in Settings differs from Caddy's | Import the infra stack first |
| Import says `… is outside the apps root and the adopted roots` | The folder is not in `AdoptedRoots` | Run the installer again with `--adopt <root>` |
| Import says `… served by a hand-written Caddy site … cannot take over` | The site routes | Leave the Public URL empty; the site stays hand-written |
| Preview shows `recreate` although nothing was edited | The compose file differs from what the container was created with (edited without `up`), or the proxy service has no alias on the shared network (v-panel adds one) | Review the compose file; to avoid the recreate, add `aliases:` on the shared network to the stack's compose (on the app page) |
| Deploy fails with `Caddy validation failed … (restored)` | Invalid directive, unknown snippet, or same host as another hand-written site | Read the job log and fix the directives or the site; the files were restored |
| Pull fails for a `…:local` image | The image is only built locally | Use Images = Pull first (pull errors are ignored, missing images are built) |
| `couldn't find env file …/.env` | The stack has no `.env` | The import creates one; if it was deleted, create an empty `.env` in the stack folder |
| `Cannot write a backup into …` | The vpanel container cannot write to the folder | Check the mounts (section 4) and folder permissions |
| Check Caddy cannot exec into the container | Wrong Caddy container name (typically when Caddy was not running during the scan) | Fix **Settings > Caddy container name** |

## 14. With an AI agent (MCP)

The same procedure over MCP ([docs/mcp.md](mcp.md), Vietnamese):

1. `scan_existing_stacks`: the same result as the Import page, plus `importInfraFirst` and `canImport` per stack.
2. `import_stack(project: "infra")`, then `import_stack(project: "n8n-arm")`. Omitted arguments use the scan's suggestions (Public URL, proxy, `proxy_directives`, `proxy_options`, `build_mode`).
3. `preview_deploy(instance: "n8n-arm")`.
4. `run_instance_action(instance: "n8n-arm", action: "deploy")`.

The MCP instructions tell agents to ask you before deploying when the preview shows `recreate`.

## 15. Limitations

- **Caddy mounts only the Caddyfile** (`./Caddyfile:/etc/caddy/Caddyfile`): `vp-*.caddy` files would not reach the container. Switch to mounting the folder (`./caddy:/etc/caddy:ro`), recreate Caddy, then scan again. v-panel only warns about it; it does not edit the infra compose file.
- **Several compose files** (`-f a.yml -f b.yml`, or `compose.override.yml`): they are merged with `docker compose config --no-interpolate` into `docker-compose.vpanel-merged.yml`; the originals stay. Comments are lost, and relative paths of files in other folders may be wrong: check with Preview.
- **Env file not named `.env`**: its content is imported and v-panel writes it as `.env`.
- **Caddy sites that route** (`handle`, `handle_path`, `route`, `redir`, `rewrite`, `respond`, `file_server`, `@matchers`, `reverse_proxy` with a matcher or `to`): cannot be taken over.
- **Containers not started by docker compose** (`docker run`): not scanned.
- **Reverse proxies other than Caddy**: not supported.
- **One server**: v-panel manages the Docker of the server it runs on.
